# 阶段 03 · 真实核心业务闭环：从用户输入到可验证结果

## 发给 AI

继续开发当前 App 的阶段 03。阅读 APPS/<slug>.md 中的“首条真实闭环”和该 App 的 PRD/技术/验收矩阵。不要从零重建项目；优先把一个真实可见、可存储、可复验的核心工作流做通，然后延伸到相邻基础能力，不接受漂亮但无功能的 UI。

【通用原则】
1. 业务结果必须由真实的业务层/硬件/文件获得；假的数据只允许存在 test fixtures，并且界面明确 Demo 模式。写入用户可见页面的数据一定可追溯至服务返回值。
2. 先用可复现测试输入完成一个端到端路径：打开 App → 用户输入/导入/授权 → 真正执行 → 更新状态 → 保存或导出 → 重启后仍可恢复 → 独立通道核验。每个操作要处理取消/拒绝/重复点击/空数据/异常权限。
3. 提前定义稳定 ID、UTC 时间/时间码单位、事务边界、输入校验、版本化 schema 和不变性契约；导入/导出应验证 URI 生命周期、文件大小、校验和、实际外部解析。
4. 仍按技能清单使用适用 Skills；每新增真实 SDK API 必须到官方 API Reference + 本地 SDK 声明核对，更新 API_AUDIT，必要时做 probe 后再接入。
5. 每完成一个纵向切片立即真实编译+跑相关测试，不一次写完大量代码后才发现 ArkTS 编译失败。所有测试命令、设备信息和结果保留可复现输出。
6. 在 App 仓库 docs/dev/IMPLEMENTATION_MATRIX.md 标记已达成真实闭环的 PRD 功能 ID；未完成的不隐藏，也不以“后续再说”删掉 PRD 合同。

【四款各自最低真实闭环，以 APPS 专项文档为准】
- LightBearing：输入机位坐标和本地日期→已有真实太阳/时区内核计算→同一个选中 UTC 时刻驱动日轨、方位/高度、阶段→存储机位→重启复现，含 DST/gap/overlap 验证；随后延伸反向寻光和计划。
- FrameMori：创建项目→真实 Camera Kit 拍照一帧→写入沙箱与索引→重新打开项目→回放帧序列→真实输出可外部查看的文件；之后延伸视频编码。
- VoxCarve：用户真实选择 WAV/音频→解析轨道/时长→实际解码/可视化波形→设置时间区间→非破坏性编辑决定→导出可在外部播放器打开的音频；转写能力需另行 SDK/设备审计。
- MacroLoom：电脑端本地 Agent→显示一次性配对码与审批→手机用户确认→设备证书/密钥校验→发送一条白名单安全动作→Agent 实际执行/拒绝→返回有 ID 的结果回执→手机显示对应真实状态。手机页面独立运行不算完整。

【收尾验收】
- 提供从零启动复现步骤、输入测试样本、操作视频/截图（仅在真实采集时）、输出文件或日志校验、重启恢复与异常回退结果。
- 针对核心闭环至少有自动化测试 + 异常测试；没有设备时标 BLOCKED/NOT_RUN，并说明可在宿主机验证哪些纯逻辑、下一步最短设备验证路径。
- 必须把实际代码改动提交当前 feature 分支并输出 SHA，形成 docs/dev/CORE_WORKFLOW.md、API_AUDIT.md、TEST_REPORT.md 的记录。未真正达成则留在阶段 03 继续修复。
